# Handoff — 2026-04-26 15:30 CDT

## What Was Done

Fixed the Block Storage I "one item per slot" constraint. The block was allowing full stacks (64) to be inserted into a single slot, voiding the remainder (e.g. left-clicking 64 items into an empty slot would consume all 64 but only store 64 — the cursor became empty).

**Root cause:** `SlotItemHandler.getMaxStackSize(ItemStack)` delegates to `handler.getSlotLimit()`, NOT to the no-arg `getMaxStackSize()`. Overriding only the no-arg version (as OpenCode had done) had zero effect on insertion logic. The fix is to override `getSlotLimit()` on the `ItemStackHandler` itself.

**Fix committed:** `f0e1755` — two files changed:

### `BlockStorageBlockEntity.java`
Added `getSlotLimit()` override to the anonymous `ItemStackHandler`:
```java
@Override
public int getSlotLimit(int slot) {
    return 1;
}
```

### `BlockStorageMenu.java`
Removed the `SingleSlot` inner class entirely (it was using a broken `set()` override that voided items) and reverted to plain `SlotItemHandler`. No custom slot class is needed — `SlotItemHandler` picks up `getSlotLimit()` automatically for both GUI interactions and automation.

## Key Gotchas

- **Do NOT override `getMaxStackSize()` (no-arg) on `SlotItemHandler` to limit slot size** — it has no effect because `safeInsert` and `moveItemStackTo` call `getMaxStackSize(ItemStack)` which delegates to `handler.getSlotLimit()`.
- **Do NOT use a custom `set()` override to limit insertion** — `moveItemStackTo` calls `p_38904_.split()` on the source stack BEFORE calling `set()` on the destination, so returning early from `set()` voids the already-split items.
- The handler's `onContentsChanged` triggers `scanMultiblock()` on the Advanced Storage Core — this is intentional and correct.
